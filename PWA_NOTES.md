# PWA notes

How the installable app is wired up, and where to change things yourself.

## App name (home screen label)

Edit `manifest.json`:

- `"name"` — full name, shown on the install prompt and app info pages.
- `"short_name"` — used for the home screen icon label. Android truncates around
  ~12 characters before ellipsis-ing, so keep this short (currently set to the
  full name, which is why it truncates to "Steps of Muh..." on install — worth
  shortening whenever you get to it).

No code changes needed — just edit the JSON and bump `CACHE_NAME` in
`service-worker.js` (see "Pushing an update" below) so installed users actually
pick up the new value.

## Icon

Three files live in `icons/`, all generated by `scripts/generate-icons.ps1`
(run with `powershell -ExecutionPolicy Bypass -File scripts\generate-icons.ps1`):

- `icons/icon-192.png` — general use, 192×192.
- `icons/icon-512.png` — general use, 512×512 (also used for the splash screen).
- `icons/icon-maskable-512.png` — 512×512, but the artwork must stay inside the
  center ~66% ("safe zone") because Android crops this one into a circle,
  squircle, or rounded square depending on the launcher. Content that touches
  the edges gets clipped.
- `icons/apple-touch-icon.png` — 180×180, iOS home screen icon (no transparency,
  iOS fills any alpha with black).

**To swap in your own design (e.g. a nalayn):** replace these four PNG files
directly at the same filenames and pixel sizes — nothing else references their
contents, only their paths, which are set in `manifest.json` (`icons` array)
and `index.html` (`<link rel="icon">`, `<link rel="apple-touch-icon">`). Keep
the maskable one's artwork inside that safe zone or it'll get cropped on many
Android launchers.

If you'd rather regenerate programmatically, edit the star-drawing logic in
`scripts/generate-icons.ps1` (uses .NET's `System.Drawing`, no external tools
needed) and rerun it.

## How updates reach installed users

Two different mechanisms, because dua content and app code update differently:

**Dua pages (content)** use *stale-while-revalidate*: opening a dua shows the
cached copy instantly, then silently re-fetches it in the background and
updates the cache. If you correct a dua's text, users who already have it
cached will see the corrected version starting from their *second* visit after
your edit goes live — the first visit after your edit still shows the old
cached copy while the refresh happens invisibly behind it. This is what makes
pages feel instant again (per the switch made after the first on-device test —
network-first was adding a visible 1-2s wait on every visit, even for content
already cached).

**App shell (`index.html`, `render.html`, `manifest.json`, `dua-core.css`,
icons, `service-worker.js` itself)** only gets a clean re-cache when you bump
`CACHE_NAME` at the top of `service-worker.js` (e.g. `v3` → `v4`). Do this
whenever you change any shell file, the icon files, or want to force everyone
onto fresh content immediately rather than waiting for the stale-while-
revalidate cycle to catch up. On the next visit while online, the browser
notices `service-worker.js` changed, installs the new version in the
background under the new cache name, and takes over — no user action needed,
though a visit while offline won't pick up the update until they're back
online.

## Local testing

`scripts/serve.ps1` + `.claude/launch.json` spin up a minimal static server
for testing service-worker behavior locally (service workers require a
secure context — `http://localhost` counts, a plain LAN IP does not).
